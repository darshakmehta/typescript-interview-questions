### **Dependency Inversion Principle (DIP)**

The **Dependency Inversion Principle (DIP)** is one of the five SOLID principles of object-oriented design. It states that:

> **"High-level modules should not depend on low-level modules. Both should depend on abstractions."**

In simpler terms:

- High-level modules (e.g., business logic) should not depend on low-level modules (e.g., specific implementations like databases or logging).
- Both should depend on abstractions (e.g., interfaces or abstract classes).

---

### **Learn the Problem**

#### **Why is DIP Important?**

- **Problem**: Tight coupling between high-level and low-level modules makes the code rigid, hard to maintain, and difficult to test.
- **Example**: If a high-level class directly depends on a specific logging implementation (e.g., `ConsoleLogger`), changing or extending the logging functionality requires modifying the high-level class.

#### **Solution**:

- Use **abstractions** (e.g., interfaces) to decouple high-level and low-level modules.
- Use **dependency injection** to provide the required dependencies at runtime.

---

### **Practice Example**

Let’s implement a `Logger` system that follows the **Dependency Inversion Principle**.

---

#### **Step 1: Define an Abstraction**

Create a `Logger` interface that defines the contract for logging.

```typescript
interface Logger {
  log(message: string): void;
}
```

---

#### **Step 2: Implement Low-Level Modules**

Create specific implementations of the `Logger` interface.

```typescript
// Console Logger
class ConsoleLogger implements Logger {
  log(message: string): void {
    console.log(`[Console] ${message}`);
  }
}

// File Logger
class FileLogger implements Logger {
  log(message: string): void {
    // Simulate writing to a file
    console.log(`[File] ${message}`);
  }
}
```

---

#### **Step 3: Create a High-Level Module**

Create a high-level class (e.g., `App`) that depends on the `Logger` abstraction, not on specific implementations.

```typescript
class App {
  private logger: Logger;

  constructor(logger: Logger) {
    this.logger = logger;
  }

  run(): void {
    this.logger.log('Application started');
    // Additional business logic
  }
}
```

---

#### **Step 4: Inject Dependencies**

Use dependency injection to provide the specific logger implementation at runtime.

```typescript
// Using ConsoleLogger
const consoleLogger = new ConsoleLogger();
const appWithConsoleLogger = new App(consoleLogger);
appWithConsoleLogger.run(); // Output: [Console] Application started

// Using FileLogger
const fileLogger = new FileLogger();
const appWithFileLogger = new App(fileLogger);
appWithFileLogger.run(); // Output: [File] Application started
```

---

#### **Step 5: Extending the System**

If you need to add a new logger (e.g., a `DatabaseLogger`), you can do so without modifying the high-level `App` class.

```typescript
// Database Logger
class DatabaseLogger implements Logger {
  log(message: string): void {
    // Simulate writing to a database
    console.log(`[Database] ${message}`);
  }
}

// Using DatabaseLogger
const databaseLogger = new DatabaseLogger();
const appWithDatabaseLogger = new App(databaseLogger);
appWithDatabaseLogger.run(); // Output: [Database] Application started
```

---

### **Key Takeaways**

1. **Dependency Inversion Principle**: High-level modules should depend on abstractions, not low-level modules.
2. **Abstractions**: Use interfaces or abstract classes to define contracts.
3. **Dependency Injection**: Inject dependencies at runtime to decouple high-level and low-level modules.
4. **Flexibility and Maintainability**: This approach makes your code more flexible, maintainable, and easier to test.

By following DIP, you ensure that your code adheres to the principle of loose coupling and is easier to extend and maintain. 🚀
