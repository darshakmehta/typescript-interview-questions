The **Single Responsibility Principle (SRP)** is one of the SOLID principles of object-oriented design. It states that a class should have only one reason to change, meaning it should have only one responsibility. Let’s break this down and refactor a `UserManager` class that violates SRP into two separate classes.

---

### Problem: Violation of SRP

Here’s an example of a `UserManager` class that handles both **user authentication** and **email notifications**. This violates SRP because the class has two responsibilities:

```typescript
class UserManager {
  // Responsibility 1: User Authentication
  login(username: string, password: string) {
    // Authenticate user
    console.log(`User ${username} logged in.`);
  }

  logout(username: string) {
    // Log out user
    console.log(`User ${username} logged out.`);
  }

  // Responsibility 2: Email Notifications
  sendEmail(userEmail: string, message: string) {
    // Send email to user
    console.log(`Email sent to ${userEmail}: ${message}`);
  }
}

// Usage
const userManager = new UserManager();
userManager.login('john_doe', 'password123');
userManager.sendEmail('john_doe@example.com', 'Welcome to our platform!');
```

---

### Refactored Solution: Adhering to SRP

To adhere to SRP, we’ll split the `UserManager` class into two separate classes:

1. **`AuthManager`**: Handles user authentication (login/logout).
2. **`EmailService`**: Handles sending email notifications.

Here’s the refactored code:

```typescript
// Responsibility 1: User Authentication
class AuthManager {
  login(username: string, password: string) {
    // Authenticate user
    console.log(`User ${username} logged in.`);
  }

  logout(username: string) {
    // Log out user
    console.log(`User ${username} logged out.`);
  }
}

// Responsibility 2: Email Notifications
class EmailService {
  sendEmail(userEmail: string, message: string) {
    // Send email to user
    console.log(`Email sent to ${userEmail}: ${message}`);
  }
}

// Usage
const authManager = new AuthManager();
const emailService = new EmailService();

authManager.login('john_doe', 'password123');
emailService.sendEmail('john_doe@example.com', 'Welcome to our platform!');
```

---

### Benefits of Refactoring

1. **Single Responsibility**:

   - `AuthManager` is only responsible for user authentication.
   - `EmailService` is only responsible for sending emails.

2. **Easier Maintenance**:

   - If the authentication logic changes, only `AuthManager` needs to be modified.
   - If the email logic changes, only `EmailService` needs to be modified.

3. **Reusability**:

   - `EmailService` can be reused in other parts of the application where emails need to be sent.

4. **Testability**:
   - Each class can be tested independently, making unit tests simpler and more focused.

---

### Advanced Refactoring: Dependency Injection

To make the code even more flexible and testable, you can use **dependency injection**. For example, you can inject the `EmailService` into another class that needs it:

```typescript
class UserNotifier {
  constructor(private emailService: EmailService) {}

  notifyUser(userEmail: string, message: string) {
    this.emailService.sendEmail(userEmail, message);
  }
}

// Usage
const emailService = new EmailService();
const userNotifier = new UserNotifier(emailService);

userNotifier.notifyUser('john_doe@example.com', 'Welcome to our platform!');
```

---

### Key Takeaways

1. **SRP** ensures that a class has only one reason to change.
2. Violations of SRP lead to tightly coupled, hard-to-maintain code.
3. Refactor classes to separate responsibilities, making the code more modular, reusable, and testable.
4. Use dependency injection to decouple classes further and improve flexibility.

By adhering to SRP, you can write cleaner, more maintainable, and scalable code!
